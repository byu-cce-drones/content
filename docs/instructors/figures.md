# Making Figures

!!! abstract "Key Takeaways"
    - Every figure on the site is SVG, drawn or generated to a fixed house style so every page
      matches. Prefer a figure with a one-sentence caption over a paragraph of prose.
    - Repeated figures are generated by Python scripts in `fig_tools/` using a shared toolkit,
      `svgkit.py`. `fig_tools/` is never published; only the SVGs it writes are.
    - File names encode where a figure came from: `wNN_figMM_short_name.svg`, one numbering
      sequence per prefix. Lab figures use a `labNN_` (or lab-specific) prefix instead.
    - Always render a new or changed figure to PNG and look at it before committing the SVG.

---

## Why SVG, and why generated

All figures are SVG so they stay crisp at any size and the labels stay searchable text, not
flattened pixels. Where a figure repeats — the same aircraft, the same controller, a drawing used
with a different number on two pages — it is built by a script in `fig_tools/` instead of drawn by
hand each time. Change the shared part once and every figure that uses it updates on the next run.

Write a one-off drawing directly as SVG when nothing about it repeats. Reach for a script when
parts repeat, or when a numbered homework variant of the same figure is needed.

`fig_tools/` holds the **tools**, not the pictures. It sits outside `docs/`, so MkDocs never
publishes the scripts — only the SVG files a script writes are committed, into the owning page's
`images/` folder.

## The toolkit

| File | Purpose |
|------|---------|
| `fig_tools/svgkit.py` | The SVG builder: palette, type sizes, arrows, callouts, the `figure_name()` helper, and PNG rendering through Inkscape |
| `fig_tools/parts.py` | Reusable drawings — the controller, the aircraft, control sticks — shared across figures |
| `fig_tools/fig_*.py` | One script per figure or figure group, one per reading or lab |

Colors and fonts come from `svgkit.PALETTE` and the shared font settings — never hard-code a new
color into a figure script. Draw generically: brand names belong in a caption or a table, never in
the picture itself, since the hardware in the lab room can change from year to year.

## House style

Fixed across every figure so the whole site reads as one set:

- Light gray background, rounded corners.
- Arial font stack throughout.
- 14 px labels, a 17 px bold title at the top of the figure, a 12 px subtitle for caveats.
- Blue leader lines ending in a dot on the part they label.
- Labels are real text in the SVG, never converted to paths — keep them editable and searchable.

## File naming

Figures are named `wNN_figMM_short_name.svg`:

- **`wNN`** is a prefix recording where the figure came from, not a folder name. `w00` is
  Measurement Fundamentals, which sits above the numbered weeks; `w01`, `w04`, `w05`, `w06` and so
  on trace back to the topic a figure was drawn for before the site was reorganized by week. The
  prefix is historical bookkeeping — it lets someone tell where an exported figure came from once
  it is out of the repository — and does not need to match the week a page is filed under today.
- **`figMM`** is the figure's number in page order, printed inside the drawing as well as in the
  file name.
- Lab figures use a lab-specific prefix instead of `wNN` — for example `labfp_` for the flight
  practice lab — with the same `figMM_short_name` pattern, living in `docs/labs/images/`.
- **`MM` runs as one sequence per prefix.** A figure that appears more than once (the same drawing
  used on two different pages) is generated once per page with its own number, so no two figures
  sharing a prefix ever collide on the same number. Several sections now share one `images/`
  folder, so check the prefix **and** the number together, not the number alone.

Scripts never spell the file name out by hand. They call `svgkit.figure_name(week, number, slug)`,
so the number in the file name can never drift away from the number the script prints inside the
drawing.

## Captions

The Markdown caption under an image is an italic line: `*Figure N: ...*`. Three numbers have to
agree — the number in the caption, the number in the file name, and the number printed inside the
drawing itself. If you renumber a figure, regenerate the SVG rather than hand-editing the file
name; the script keeps all three in sync for you.

!!! warning "Never leave a caption with nothing above it"
    A `*Figure N: ...*` line with no image above it is worse than no caption at all — it tells a
    student a figure exists and then shows them nothing. If you remove or replace an image, remove
    or update its caption in the same edit.

## Provenance on borrowed images

A borrowed image's original file name is part of its provenance. Before renaming a Wikimedia or
other third-party image into the `wNN_figMM_` scheme, make sure its caption already records the
source and the license — once it is renamed, the trail back to where it came from is gone unless
the caption carries it.

## Running a script

```
python fig_tools/fig_measurement.py --png
python fig_tools/fig_measurement.py --out docs/gen_reading/images
```

- With no flags, a script writes its SVGs into `review/`, for a look before anything is committed.
- `--png` additionally renders a PNG next to each SVG using Inkscape, which is the fastest way to
  check a figure without opening a browser. The PNG is for checking only — the published site uses
  the SVG.
- `--out <folder>` writes straight to the owning page's `images/` folder, once you are ready to
  commit — for example `--out docs/gen_reading/images` for a Week 5-and-above reading, or
  `--out docs/labs/images` for a lab figure.

If a script reports that Inkscape was not found, point it at the executable directly:

```
set INKSCAPE=C:\Program Files\Inkscape\bin\inkscape.com
```

!!! tip "Look at every figure before committing"
    Render to PNG (or open the SVG in a browser) and actually look at it — check that labels do not
    overlap, that the leader lines point at the right part, and that the figure number printed
    inside the drawing matches the caption. This is quick and it is the only way to catch a mistake
    a strict build cannot see.
